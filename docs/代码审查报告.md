## 一、严重问题（会影响修复正确性 / 让兜底静默失效）

### 1. `FragmentGuard.isSupportedSignature` 的参数白名单过窄 —— 第 4 层兜底存在"静默不生效"的风险

> **验证状态：部分验证（需在目标 App 上确认实际签名）。** 源码逻辑与过滤条件已确认；
> "该 App 所用的 androidx 版本里 `performCreate` 究竟是哪个签名"**未能确认**——
> 设备当前离线，且拉取 androidx 源码时被截断在 `performCreate` 定义之前。
> 因此本条按"**潜在风险 + 防御性缺陷**"处理，不宜断言"从未生效"。

`FragmentGuard.java:56-67` 用 `getDeclaredMethods()` 遍历并用 `isSupportedSignature` 过滤：

```java
private static boolean isSupportedSignature(Method m) {
    Class<?>[] pt = m.getParameterTypes();
    if (pt.length == 0 || pt.length > 2) return false;            // ← 硬上限 2
    for (Class<?> p : pt) {
        if (p != Bundle.class && p != boolean.class) return false; // ← 白名单过窄
    }
    return true;
}
```

已确认的问题（与目标版本无关，属于防御性缺陷）：

1. **参数个数硬上限为 2、类型白名单只允许 `Bundle` 与 `boolean`**。
   如果某版本 `Fragment.performCreate` 的签名不在这个白名单内
   （例如带 `boolean, boolean` 或其它参数），会**被静默跳过**，
   `XposedBridge.hookMethod` 一次都不会被调用。
2. **挂钩数为 0 时日志措辞具有误导性**。`FragmentGuard.java:69-70` 打印：

   ```
   FragmentGuard: performCreate 挂钩数=0（未找到，业务类兜底仍会生效）
   ```

   但同一文件里"业务类兜底"找不到时的日志是：

   ```
   未找到业务类 …（可能被混淆/加固，不影响框架层兜底）
   ```

   两条日志互相把责任推给对方。**当两者同时失败时**（App 被混淆/加固 + `performCreate`
   签名不匹配），第 4 层"最后一道防线"完全不存在，而日志读起来像是"还有兜底"。
   这是本条最实际的危害：**兜底失效是静默的**。

**建议（低风险、不必等确认即可做）**：
1. 放宽过滤：只要求"首个参数是 `Bundle`，其余参数为 `boolean`/`int`"，去掉 `pt.length > 2` 的硬上限；
   更彻底的做法是不做白名单，对所有名为 `performCreate` 的 `private`/包内方法都挂钩；
2. `hooked == 0` 时用 `XLog.e` 明确写出"**本层未生效**"，
   并在安装完成后汇总一次"五层各自是否生效"的结论；
3. 安装后主动验证：至少记录每一层挂钩成功的计数，便于现场一眼看出哪层没挂上。

### 2. `FragmentGuard` 吞掉异常后修补 `mIsCreated` 会**破坏框架状态机**，导致同一个 NPE 反复重试

> **验证状态：已确认（依据 androidx 官方源码，本轮已核实）。**
> 证据来源：`androidx/fragment/app/Fragment.java` 与 `FragmentStateManager.java`（androidx-main）。
> 关键源码事实均已在本地核对行号，见下。

#### 事实 1：`mState` 不是由 `performCreate` 推进的，而是由 `moveToExpectedState()` 的循环推进

`FragmentStateManager.create()` 的实现是：

```java
void create() {
    ...
    if (!mFragment.mIsCreated) {
        mFragment.performCreate(savedInstanceState);   // ← 业务 onCreate 在这里抛 NPE
        mDispatcher.dispatchOnFragmentCreated(...);
    } else {
        mFragment.mState = Fragment.CREATED;           // ← 只有 else 分支才置 mState
        mFragment.restoreChildFragmentState();
    }
}
```

而 `mState = CREATED` 的推进发生在**外层循环**里：

```java
void moveToExpectedState() {
    ...
    while ((newState = computeExpectedState()) != mFragment.mState) {
        if (newState > mFragment.mState) {
            switch (mFragment.mState + 1) {
                case Fragment.CREATED:
                    create();                 // ← 抛异常就直接跳出整个方法
                    ...
```

**结论**：`performCreate` 抛 NPE 时，`create()` 未返回，**`mState` 仍停在 `ATTACHED`**，
异常穿透 `moveToExpectedState()` 冒泡上去。

#### 事实 2：`mState` 不推进 ⇒ 下一次 `moveToExpectedState()` 会**再次**走到 `create()`

循环条件是 `computeExpectedState() != mState`。因为 `mState` 没有前进、
`computeExpectedState()` 仍返回 `CREATED`，所以**下一次调度会重新调用 `create()` →
再次 `performCreate()` → 再次抛同样的 NPE**。

这解释了真机上"吞掉一个异常后换个地方又崩"的现象：
`FragmentGuard` 目前的 `return null`（吞掉）并没有修复状态机，只是把同一个异常
**推迟到下一次 `moveToExpectedState()`**。

#### 事实 3（额外发现）：`mIsCreated` 在 `Fragment.java` 里**从不赋值**，`trySetBoolean(mIsCreated, true)` 是危险操作

对 `Fragment.java` 全文检索 `mIsCreated` 只有两处：

```
298:  boolean mIsCreated;                    // 声明（package-private）
1388: && mFragmentManager != null && isAdded() && mIsCreated   // 读取
```

**整个文件中没有任何 `mIsCreated =` 赋值**——它由 `FragmentStateManager` 在
"保留 Fragment（retained）"路径上设置。

而 `FragmentStateManager.create()` 的第一句就是 `if (!mFragment.mIsCreated)`。
因此 `FragmentGuard.trySetBoolean(fragment, "mIsCreated", true)` 的实际效果是：
**让框架认为这个 Fragment 已经创建过，从而跳过 `performCreate` 与
`dispatchOnFragmentCreated`，只把 `mState` 置为 `CREATED`。**

后果：
- `onCreate` 从未真正跑完（业务侧未初始化）；
- `dispatchOnFragmentCreated`（生命周期分发、`mChildFragmentManager.dispatchCreate()`）
  被跳过 ⇒ 子 Fragment 不会创建、`Lifecycle` 不推进；
- 界面表现为**空白/半死状态**，且 `ViewModelProvider`、`SavedStateRegistry` 等
  依赖 `CREATED` 分发的组件全部缺失。

换句话说，**这一行把"崩溃"换成了"静默的坏状态"**，正是审查报告里所说的
"比崩溃更难定位"的具体机制。

#### 与第 3 层的关系

第 3 层（`RongGuard.getEventBus()` 兜底 / 占位单例）才是真正让
`BaseNewContactFragment.onCreate` **不再抛异常**的那一层。
只要第 3 层生效，第 4 层根本不需要吞异常，`mState` 也就不会被卡住。
因此第 4 层的"吞异常 + 打补丁"路径属于**不该被触发的兜底**。

#### 建议（高风险，需谨慎）

1. **首选：让第 4 层不再需要吞异常。** 确认第 3 层在所有时序下都生效
   （`getEventBus()` 兜底 + 占位单例），第 4 层只保留"提前初始化"作用，
   把 `repairAfterSwallow` 里的 `mIsCreated` 赋值**去掉**。
2. 若必须保留吞异常路径，**至少要同时把 `mState` 置为 `CREATED`(1)**，
   否则下一次调度会重试并再次抛异常；但这仍会导致子 Fragment 未创建，
   属于"能跑但不完整"，应在日志里明确标注降级。
3. **不要设置 `mIsCreated=true`**：它会让框架跳过 `performCreate`，
   危害大于收益。
4. 以上都属于对第三方框架内部状态的写入，**风险高**，建议在设备上
   用"验证补丁"路径确认第 3 层单独生效后再移除这段兜底逻辑。

### 2.1 ✅ 修复结果与真机验证（已完结）

**已按上述"建议 1 + 2 + 3"实施**（`FragmentGuard.repairAfterSwallow`）：

- ❌ **删除** `trySetBoolean(fragment, "mIsCreated", true)` —— 源码已证实该字段
  在整个 `Fragment.java` 中**只被已废弃的 `setUserVisibleHint()` 读取一次**，
  把它置 true 会让 `FragmentStateManager.create()` 跳过 `performCreate` 与
  `dispatchOnFragmentCreated`，把崩溃换成静默坏状态。
- ✅ **新增** `trySetInt(fragment, "mState", Fragment.CREATED)` —— 让状态机前进一步，
  避免 `moveToExpectedState()` 的 `while` 反复重试同一个 `create()`。
  常量**不硬编码**，通过 `stateConstantOf()` 沿父类链反射读取。
- ✅ 保留 `mCalled` 修补与子 `FragmentManager` 的 `dispatchCreate` 补做。

**修复过程中发现并修掉的两个自身缺陷**（都是真机验证暴露的）：

1. **`isSwallowableForRedirected` 未解包反射异常**（回归）：
   `XposedBridge.invokeOriginalMethod` 抛出的异常被包成
   `InvocationTargetException`，原实现只看顶层类型与一层 cause，导致本该吞掉的
   业务 NPE 被误判为"不可吞"而重新抛出。真机日志：
   `E NahangFix: 被重定向 Activity 的 callActivityOnCreate 抛出了不可吞的异常，原样放行`
   → 已改为沿 cause 链循环解包（最多 8 层），`Error` 一律放行。
2. **`stateConstantOf` 用了 `getDeclaredField`**（不查父类）：
   `getClass()` 给的是业务子类（`BaseNewContactFragment`），而 `CREATED`
   声明在 androidx 的 `Fragment` 上，导致常量永远解析失败、`mState` 静默不修补。
   → 已改为沿父类链查找。

**真机 A/B 对照（Android 16 / API 36，release 包）**：

| 场景 | 复现路径 | 结果 |
|---|---|---|
| **A 补丁开启** | 冷启动 → HOME → `kill -9` 主进程 → `am start` | ✅ **无崩溃**；重定向 + 吞异常正常；`imStatus=CONNECTED`（消息可用）；MainActivity 正常前台 |
| **B 补丁关闭** | 同上（放置 `nahangfix.off`） | ✅ **复现原始崩溃**：`FATAL EXCEPTION` → `NullPointerException: RongContext.getEventBus()` @ `BaseNewContactFragment.java:48` |

**一个重要的验证发现**：`am start -n cn.edu.nchu.nahang/.ui.MainActivity` 会**跳过 App
自己的初始化流程**（真实入口是 `.ui.SplashActivity`），此时会撞上**另一个** NPE

那不是本模块要修的目标崩溃。因此验证崩溃必须走"冷启动 → HOME → 杀 → 恢复"，

### 3. `EarlyRestoreGuard` 的生命周期钩子会**吞掉被放弃实例的所有异常**，包括不该吞的

```java
if (activity == sRedirectedActivity) {
    try { ... return ...; }
    catch (Throwable t) {
        XLog.w("已吞掉被重定向 Activity 的 " + name + " 异常（该实例正在被丢弃）：", t);
        markCalled(activity);
        return null;
    }
}
```

`Throwable` 会把 `OutOfMemoryError`、`StackOverflowError` 一并吞掉；
更实际的问题是：这段逻辑在 `callActivityOnCreate/Start/Resume/Pause/Stop/Destroy/Restart`
**七个**回调里都会命中，任何一个异常都被静默吞掉，只留一行 `w` 日志。

**后果**：真出问题时表现为"App 不崩，但行为诡异且没有任何显式报错"，
       比崩溃更难定位。而且这套"吞异常 + 补 `mCalled`"的做法对 `onDestroy`
       之后的回调是否仍在同一实例上并无保证（`sRedirectedActivity` 只在
       `onDestroy` 成功返回时才清空，走到 catch 分支时**不会被清空**，
       于是该 Activity 的后续回调会一直被吞）。

**建议**：
1. 只吞 `RuntimeException`/`Error` 中的 `NullPointerException`、`IllegalStateException`，
   其余照常抛出；
2. 在 catch 分支里也清空 `sRedirectedActivity`，避免引用泄漏与"永久吞异常"。

## 二、中等问题（逻辑不严谨 / 误判风险）

### 4. `PatchState.load()` 的"已注入"判定存在误报

```java
boolean pidMatch = !s.heartbeatPid.isEmpty() && !s.pid.isEmpty()
        && (" " + s.pid + " ").contains(" " + s.heartbeatPid + " ");
```

`pidof <pkg>` 会返回**主进程 + :ipc 等多个 pid**，而模块只写入**主进程**自己的 pid。
判定要求 `heartbeatPid` 恰好等于 `s.pid`（此处 `s.pid` 取的是 `firstLineOf(pidPart)`，
即第一个 pid，通常就是主进程）。这一条逻辑本身能work，但：

`firstLineOf(pidPart)` 取的是 `pidof` 输出的**第一行**；若 `pidof` 先返回 `:ipc` 的 pid
（顺序不保证），`s.pid` 就不是主进程 pid，`pidMatch` 为 false →
面板误报"模块未注入"。

**建议**：不取第一行，而是把 `pidof` 的全部 pid 与 `heartbeatPid` 做集合包含判断。

### 5. `RongGuard.repairsDisabled()` 的缓存永远不会失效

```java
private static volatile Boolean sRepairsDisabled;
static boolean repairsDisabled() {
    Boolean cached = sRepairsDisabled;
    if (cached != null) return cached;   // ← 一旦读过就永久缓存
    ...
    sRepairsDisabled = off;
    return off;
}
```

开关文件是**运行期**由模块 App 通过 root 修改的。模块侧一旦在进程早期读过一次
（例如 `Application.onCreate` 阶段的启动观测），之后无论开关怎么变都不再重新读。

**后果**：A/B 对照时，"刚把 off 文件删掉"的进程仍然按"只观测"运行，
导致"验证补丁"却仍复现崩溃、或反之。README/UI 里也提到"开关按进程缓存，
切换后请强制停止目标 App"，说明这个行为是**已知并被文档化的**，
但它本质上是设计缺陷而非特性，且用户极易忘记。

**建议**：给缓存加时间/TTL（例如 2 秒），或至少在文件 mtime 变化时失效缓存。
本轮修复中 **未改动**（用户已明确要求停止修这个问题）。

### 6. `ImStatusWatcher.persist()` 的 `sWritten` 去重会让"最终状态"丢写

```java
if (!force && value.equals(sWritten)) return;
sWritten = value;
StateFile.write(sContext, "ImStatusWatcher", value);
```

若 `StateFile.write` **失败**（外部存储未挂载，代码里明确说"稍后重试"），
`sWritten` 已经被更新成新值，后续轮询虽然 `force=true` 会补写（挂上了就行），
但如果是 `record()` 触发的普通写失败，则**该状态在非 force 路径下永远不会再写**，
只能等下一次状态变化或 60 秒后的周期性 force。

**建议**：写失败后回滚 `sWritten`，或在 `StateFile.write` 返回成功与否。

### 7. `XLog.i/w/e` 在模块 App 自己进程里调用 `XposedBridge.log` 会抛异常

`XLog` 的四个方法都无条件调用 `XposedBridge.log(...)`：

```java
static void i(String msg) {
    Log.i(TAG, msg);
    XposedBridge.log(TAG + " | " + msg);   // ← 无 Xposed 环境时抛
}
```

这些 `XLog` 全部定义在 `app/src/main/java` 下（同一个 APK）。模块 App 自己的进程
（`com.dsh.nahangfix`）里没有 Xposed 环境，`XposedBridge.log` 会抛
`IllegalStateException`/`NoClassDefFoundError`。

**后果**：本轮调试中**真实踩到过**——`ReproRunner`/`repro` 流程里的心跳线程调用
`XLog.marker` 后线程直接被打死，表现为"步骤/通知不再刷新"。当时是把流程里的调用
改成 `android.util.Log` 绕过的（见 `ReproRunner` 中多处注释），**根因未修**。

**建议**：在 `XLog` 内部把 `XposedBridge.log` 包在 try/catch 里（或加一个
"是否在 Xposed 环境"的静态判定），从根上消除这个坑，而不是在每个调用点绕。

### 8. `MainActivity.runRepro` 与 `ReproRunner.start` 之间存在状态窗口

```java
suppressSwitchCallback = true;
switchRepairs.setChecked(!expectCrash);
suppressSwitchCallback = false;
switchRepairs.setEnabled(false);
...
ReproRunner.start(expectCrash, cb);
```

`runRepro` 先在 UI 上把开关拨到目标态，真正的 off 文件由流程第一步写。
若用户在 `setEnabled(false)` 之前（同一帧内）触发开关回调，会手动调用
`applySwitch` 写一次 off 文件，随后流程再写一次——顺序竞争。
实践中难以触发（同一消息循环内），但 `handleAutoTest` 走 `postDelayed(2000)`
时窗口更长。

**建议**：`ReproRunner.start` 返回值告知是否真正启动，成功后再禁用控件并同步开关。

## 四、值得肯定的部分

- `RootShell` 的"全局截止时间"设计（本轮刚修）解决了多路回退导致超时翻倍的问题；

  是针对本机 `su` 10s+ 开销的正确优化；
- `LSPosed` 的 `CATEGORY_INFO` 入口方案正确，且已在真机上验证。
